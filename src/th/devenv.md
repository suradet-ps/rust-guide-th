# สภาพแวดล้อมการพัฒนา

## Rustup

[Rustup] เป็นตัวติดตั้งชุดเครื่องมือ (toolchain) ของ Rust นอกจากนี้ยังช่วยให้
สลับระหว่างรูปแบบต่าง ๆ ของชุดเครื่องมือ (stable, beta, nightly) จัดการ
การติดตั้งคอมโพเนนต์เพิ่มเติม และดูแลคอมโพเนนต์เหล่านั้นให้ทันสมัยอยู่เสมอ

<div class="warning">

จากมุมมองด้านความปลอดภัย `rustup` ดาวน์โหลดทุกอย่างผ่าน HTTPS
แต่ยังไม่ตรวจสอบลายเซ็นของไฟล์ที่ดาวน์โหลด การป้องกันการโจมตีแบบดาวน์เกรด
(downgrade attack) การปักหมุดใบรับรอง (certificate pinning) และการตรวจสอบลายเซ็น
ยังอยู่ระหว่างการพัฒนา
ในบางกรณี อาจเหมาะสมกว่าที่จะเลือกใช้วิธีการติดตั้ง
ทางเลือกที่ระบุไว้ในส่วน *Install* ของเว็บไซต์ทางการของ Rust

</div>

[rustup]: https://github.com/rust-lang/rustup.rs

### เอดิชันของ Rust (Rust Editions)

ภาษา Rust มีหลายรูปแบบที่เรียกว่า *เอดิชัน (edition)* อยู่ร่วมกัน

แนวคิดเรื่องเอดิชันถูกนำมาใช้เพื่อทำให้การนำฟีเจอร์ใหม่ ๆ ไปใช้ชัดเจนขึ้น
และเป็นไปอย่างค่อยเป็นค่อยไป จะมีเอดิชันใหม่ออกมาทุกสองถึงสามปี
ดังที่ระบุไว้ใน [คู่มือ Rust @rust-edition-guide] แต่ไม่ได้หมายความว่าฟีเจอร์ใหม่
และการปรับปรุงจะเผยแพร่เฉพาะในเอดิชันใหม่เท่านั้น

เอดิชันบางรายการนำคำสงวน (keyword) และโครงสร้างภาษาใหม่ ๆ เข้ามา ข้อเสนอแนะสำหรับ
การพัฒนาแอปพลิเคชันที่ปลอดภัยจึงยังคงเชื่อมโยงอย่างใกล้ชิดกับฟีเจอร์ของภาษา
ที่ใช้ในแอปพลิเคชันเหล่านั้น มากกว่ากับเอดิชันของ Rust
ในส่วนที่เหลือของแนวทางนี้ จะพยายามอย่างเต็มที่ในการเน้นโครงสร้าง
และฟีเจอร์ของภาษาที่เฉพาะกับเอดิชันใดเอดิชันหนึ่งของ Rust

<div class="note">

ไม่มีการแนะนำเอดิชันใดเป็นการเฉพาะ ตราบใดที่ผู้ใช้ปฏิบัติตาม
ข้อเสนอแนะที่เกี่ยวข้องกับฟีเจอร์ที่เอดิชันที่เลือกใช้มอบให้

</div>

[edition guide]: https://doc.rust-lang.org/edition-guide/


### ชุดเครื่องมือ stable, nightly และ beta

โดยไม่ขึ้นอยู่กับการเลือกเอดิชันซึ่งช่วยให้เลือกรูปแบบ (ชุดของฟีเจอร์)
ของภาษา Rust ชุดเครื่องมือ Rust มีให้ในสามเวอร์ชันที่แตกต่างกัน
เรียกว่า *ช่องทางเผยแพร่ (release channel)*:

- รีลีส *nightly* ถูกสร้างขึ้นวันละครั้ง
- รีลีส *beta* ถูกสร้างขึ้นทุกหกสัปดาห์ จาก *nightly* ที่ได้รับการเลื่อนขั้น
- รีลีส *stable* ถูกสร้างขึ้นทุกหกสัปดาห์ จาก *beta* ที่ได้รับการเลื่อนขั้น

เมื่อต้องสลับไปมาระหว่างชุดเครื่องมือต่าง ๆ สิ่งสำคัญคือต้องตรวจสอบไม่เพียงว่า
ชุดเครื่องมือเริ่มต้น (default) คืออะไร แต่ยังต้องตรวจสอบด้วยว่าขณะนี้
มีการตั้งค่าการแทนที่ (override) ไว้สำหรับไดเรกทอรีใด ๆ หรือไม่

<div class="example">

```shell
$ pwd
/tmp/foo
$ rustup toolchain list
stable-x86_64-unknown-linux-gnu (default)
beta-x86_64-unknown-linux-gnu
nightly-x86_64-unknown-linux-gnu
$ rustup override list
/tmp/foo                                    nightly-x86_64-unknown-linux-gnu
$
```

ตัวอย่างนี้แสดงว่าชุดเครื่องมือ `stable-x86_64-unknown-linux-gnu` เป็นชุดเครื่องมือเริ่มต้น
แต่ถูกแทนที่ในไดเรกทอรี `/tmp/foo` ด้วย `nightly-x86_64-unknown-linux-gnu`

</div>

<div class="reco" id="DENV-STABLE" type="กฎ" title="ใช้ชุดเครื่องมือคอมไพล์ที่เป็น stable">

การพัฒนาแอปพลิเคชันที่ปลอดภัยต้องทำโดยใช้ชุดเครื่องมือที่เป็น stable
อย่างสมบูรณ์ เพื่อจำกัดบั๊กที่อาจเกิดขึ้นในคอมไพเลอร์ รันไทม์ หรือเครื่องมือต่าง ๆ

</div>

เมื่อใช้คำสั่งย่อย (subcommand) ของ `cargo` บางคำสั่งที่ต้องใช้คอมโพเนนต์ nightly
ควรเรียกใช้โดยสลับชุดเครื่องมือเฉพาะจุดเท่านั้น แทนที่จะ
สลับชุดเครื่องมือทั้งหมดโดยตรง

<div class="example">

ตัวอย่างเช่น การเรียกใช้ `rustfmt` เวอร์ชันล่าสุด (nightly):

```shell
$ rustup toolchain list
stable-x86_64-unknown-linux-gnu (default)
beta-x86_64-unknown-linux-gnu
nightly-x86_64-unknown-linux-gnu
$ rustup run nightly cargo fmt
$ # or
$ cargo +nightly fmt
$
```

</div>

### การรับประกันระดับชั้น (tier) ของ Rustc

เนื่องจากแบ็กเอนด์ของ Rustc ใช้ [LLVM] เป็นพื้นฐาน จึงสืบทอดและจำแนกเป้าหมายการคอมไพล์ (target) ที่รองรับออกเป็นระดับชั้น (tier) เพื่อบอกว่าแต่ละแบ็กเอนด์ได้รับความเสถียรและการทดสอบมากน้อยเพียงใด

[LLVM]: https://llvm.org/

<div class="example">

รายการเป้าหมายของ Rust แสดงได้ด้วยคำสั่งต่อไปนี้

```shell
$ rustup target list
...
wasm32-unknown-emscripten
wasm32-unknown-unknown (installed)
wasm32-wasip1
...
x86_64-unknown-illumos
x86_64-unknown-linux-gnu (installed)
x86_64-unknown-linux-gnux32
...

```

ในที่นี้เป้าหมาย `wasm32-unknown-unknown` และ `x86_64-unknown-linux-gnu` ได้รับการติดตั้งแล้ว

</div>

#### Tier 1 - รับประกันว่าใช้งานได้

เป้าหมายนี้ได้รับการตรวจสอบกลั่นกรองอย่างเต็มที่จากชุมชน ผ่านชุดการทดสอบทั้งหมด ได้รับการทดสอบการถดถอย (regression testing) เป็นประจำ และได้รับการอัปเดตให้ทันสมัยอยู่เสมอเมื่อมีการเปิดตัวเวอร์ชันใหม่ ในทางปฏิบัติ คุณสามารถพึ่งพาการสร้างโค้ดที่สม่ำเสมอ เอบีไอ (ABI)[^abi] ที่เสถียร และประสิทธิภาพที่คาดเดาได้ เป้าหมาย Tier 1 จึงอาจมองได้ว่าเป็น "รับประกันว่าใช้งานได้"

[^abi]: อินเทอร์เฟซไบนารีของแอปพลิเคชัน (Application Binary Interface)

#### Tier 2 - รับประกันว่าคอมไพล์ผ่าน

ซอร์สโค้ดของเป้าหมายนี้คอมไพล์ผ่านอย่างราบรื่น แต่ไม่ได้รับการทดสอบหรือบำรุงรักษาในระดับเดียวกับ Tier 1 อาจขาดความครอบคลุมเต็มรูปแบบในชุดการทดสอบ และการปรับแต่งบางอย่างหรือฟีเจอร์ใหม่ของ [LLVM] อาจหายไปหรือไม่เสถียร ผู้ใช้ยังคงสร้างโค้ดสำหรับแบ็กเอนด์เหล่านี้ได้ แต่ควรคาดว่าจะพบปัญหาการชำรุดเสียหายเป็นครั้งคราวหรือจำเป็นต้องแพตช์ด้วยตนเอง เป้าหมาย Tier 2 อาจมองได้ว่าเป็น "รับประกันว่าคอมไพล์ผ่าน" แต่ไม่ใช่ "รับประกันว่าใช้งานได้"

#### Tier 3

เป้าหมาย Tier 3 ไม่ได้รับการสนับสนุนอย่างเป็นทางการ



การจำแนกระดับชั้นช่วยให้นักพัฒนาเลือกเป้าหมายที่สอดคล้องกับระดับความเสี่ยงที่ยอมรับได้: Tier 1 สำหรับงานระดับการผลิต (production-grade) Tier 2 สำหรับสถาปัตยกรรมเชิงทดลองหรือเฉพาะกลุ่มที่ยังได้รับการสนับสนุนไม่เต็มที่

<div class="reco" id="DENV-TIERS" type="กฎ" title="ใช้เฉพาะ tier 1 ของ `rustc` สำหรับซอฟต์แวร์ที่ความปลอดภัยเป็นสิ่งสำคัญยิ่ง">

ต้องใช้เป้าหมาย tier 1 ของ Rustc และชุดเครื่องมือที่ได้รับการรับรองสำหรับระบบที่ความปลอดภัยเป็นสิ่งสำคัญยิ่ง

</div>

รายการเป้าหมายที่รองรับอย่างครอบคลุมมีอยู่ใน [หนังสือ Rust @rustc-book]

## Cargo

เมื่อ Rustup ตั้งค่าชุดเครื่องมือ Rust ที่เหมาะสมเรียบร้อยแล้ว [Cargo] จะพร้อมใช้งาน
ผ่านโปรแกรมบรรทัดคำสั่ง (command line) `cargo` Cargo เป็นตัวจัดการแพ็กเกจของ Rust
และมีบทบาทพื้นฐานในงานพัฒนา Rust ส่วนใหญ่:

- จัดโครงสร้างโปรเจกต์โดยจัดเตรียมโครงร่าง (skeleton) ของโปรเจกต์ (`cargo new`)
- คอมไพล์โปรเจกต์ (`cargo build`)
- สร้างเอกสารประกอบของโปรเจกต์ (`cargo doc`)
- เรียกใช้การทดสอบ (`cargo test`) และการวัดประสิทธิภาพ (benchmark) (`cargo bench`)
- จัดการและดาวน์โหลดดีเพนเดนซี (dependency)
- ทำให้แพ็กเกจเผยแพร่ได้และเผยแพร่แพ็กเกจเหล่านั้นบน [`crates.io`]
- ยังทำหน้าที่เป็นส่วนหน้าสำหรับเรียกใช้เครื่องมือเสริม เช่น เครื่องมือที่
  อธิบายไว้ด้านล่าง ในรูปแบบของคำสั่งย่อย (sub-command)

Cargo ช่วยให้สามารถแก้ไขดีเพนเดนซีได้โดยอัตโนมัติก่อนการคอมไพล์
ด้วยการตรวจสอบเช็กซัม (checksum) ของดีเพนเดนซีเหล่านั้น
ไฟล์ `Cargo.lock` เก็บเช็กซัมของดีเพนเดนซีทั้งหมด ซึ่งจะนำไปเปรียบเทียบกับ
ค่าที่ดาวน์โหลดมา หากตรวจพบความแตกต่าง การคอมไพล์จะล้มเหลว:

```
error: checksum for `sha256 v1.6.0` changed between lock files

this could be indicative of a few possible errors:

    * the lock file is corrupt
    * a replacement source in use (e.g., a mirror) returned a different checksum
    * the source itself may be corrupt in one way or another

unable to verify that `sha256 v1.6.0` is the same as when the lockfile was generated
```

เมื่อไม่มีไฟล์ `Cargo.lock` ไฟล์นี้จะถูกสร้างขึ้นในการบิลด์ครั้งแรก และบันทึก
เช็กซัมของดีเพนเดนซีต่าง ๆ โดยยึดตามนโยบาย TOFU (*Trust On First Use*)
ไฟล์นี้ยังสร้างด้วยตนเองได้ด้วย `cargo generate-lockfile` หากไฟล์มีอยู่แล้ว
ไฟล์จะถูกเขียนทับด้วยเวอร์ชันล่าสุดที่มีอยู่ของทุกเครต

<div class="reco" id="DENV-CARGO-LOCK" type="กฎ" title="ติดตาม Cargo.lock ในระบบควบคุมเวอร์ชัน">

ต้องเก็บไฟล์ `Cargo.lock` ไว้ในระบบควบคุมเวอร์ชัน (version control system)

</div>

<div class="warning">

ยังมีการอภิปรายกันอย่างต่อเนื่องเกี่ยวกับวิธีที่ดีที่สุดในการปกป้อง
และตรวจสอบเครต *ในการดาวน์โหลดครั้งแรก* (ตามกฎ TOFU)
ในปัจจุบัน ความปลอดภัยของการดาวน์โหลดครั้งแรกอาศัยความปลอดภัยที่ดีของ
เว็บไซต์ [`crates.io`] และที่เก็บ (repository) ที่โฮสต์บน GitHub ซึ่งบรรจุ
ดัชนีรีจิสทรี (registry index) ในบางกรณี อาจเหมาะสมกว่าที่จะเลือกใช้วิธีการ
ติดตั้งดีเพนเดนซีแบบทางเลือก

</div>

Cargo มีคำสั่งและตัวเลือกที่แตกต่างกันมากมายเพื่อปรับกระบวนการบิลด์ให้
เหมาะกับความต้องการของโปรเจกต์ โดยส่วนใหญ่ผ่านไฟล์แมนิเฟสต์ (manifest) `Cargo.toml` สำหรับ
รายละเอียดฉบับสมบูรณ์ โปรดดู [หนังสือ Cargo @cargo-book]

ในระหว่างการพัฒนาแอปพลิเคชันที่ปลอดภัย ตัวเลือกบางอย่างอาจต้อง
ให้ความสนใจเป็นพิเศษ

Cargo มีแนวคิดเรื่อง *โปรไฟล์ (profile)* โดยมีโปรไฟล์ในตัวสี่โปรไฟล์ ได้แก่ `dev`, `release`, `test` และ `bench`
ซึ่งจะถูกนำไปใช้ตามคำสั่ง `cargo` ที่เรียกใช้

ตัวอย่างเช่น `cargo build` ใช้โปรไฟล์ `dev` และ `cargo build --release` หรือ `cargo install`
ใช้โปรไฟล์ `release`

โปรไฟล์สามารถสร้าง/แก้ไขได้ในส่วน `[profile.*]` ตัวอย่างเช่น:

- ตัวแปร [`debug-assertions`] ควบคุมว่าเปิดใช้การตรวจสอบดีบัก (debug assertion) หรือไม่
- ตัวแปร [`overflow-checks`] ควบคุมว่ามีการตรวจสอบการล้น (overflow) สำหรับ
  การคำนวณจำนวนเต็มหรือไม่

การเขียนทับตัวเลือกเริ่มต้นอาจทำให้บั๊กไม่ถูกตรวจพบ แม้จะใช้
โปรไฟล์ `dev` ซึ่งโดยปกติเปิดใช้การตรวจสอบขณะรันไทม์ (ตัวอย่างเช่น โปรไฟล์นี้ไม่ได้เปิดใช้
[การตรวจสอบการล้นของจำนวนเต็ม](integer.md#chapter-integer))

<div class="reco" id="DENV-CARGO-OPTS" type="กฎ" title="คงค่าเริ่มต้นไว้สำหรับตัวแปรสำคัญในโปรไฟล์ของ cargo">

ต้องไม่เขียนทับค่าของตัวแปร [`debug-assertions`] และ [`overflow-checks`]
ในส่วนของโปรไฟล์สำหรับการพัฒนา (`[profile.dev]` และ `[profile.test]`)

</div>

Cargo ยังมีวิธีอื่นในการตั้งค่าคอนฟิกูเรชันและเปลี่ยนแปลงพฤติกรรมบน
ระบบหนึ่ง ๆ ซึ่งมีประโยชน์มาก แต่ก็อาจเป็นเรื่องยากที่จะรู้และจดจำ
ตัวเลือกทั้งหมดที่ถูกใช้อยู่จริงในขณะนั้น และโดยเฉพาะตัวเลือกที่
ส่งต่อไปยังคอมไพเลอร์ สุดท้ายแล้ว สิ่งนี้อาจส่งผลต่อความมั่นใจ
และความทนทานของกระบวนการบิลด์ จึงควรเลือกที่จะรวบรวมตัวเลือกและแฟล็กของคอมไพเลอร์
ไว้ในไฟล์คอนฟิกูเรชัน `Cargo.toml` ตัวอย่างเช่น ในกรณีของตัวแปรสภาพแวดล้อม
(environment variable) `RUSTC_WRAPPER` ซึ่งอาจถูกใช้เพื่อสร้าง
โค้ดบางส่วนหรือเรียกใช้เครื่องมือภายนอกก่อนการคอมไพล์ Rust ควรใช้
ฟีเจอร์บิลด์สคริปต์ (build script) ของ Cargo แทน

<div class="reco" id="DENV-CARGO-ENVVARS" type="กฎ" title="คงค่าเริ่มต้นของตัวแปรสภาพแวดล้อมของคอมไพเลอร์เมื่อเรียกใช้ cargo">

ต้องไม่เขียนทับตัวแปรสภาพแวดล้อม `RUSTC`, `RUSTC_WRAPPER` และ `RUSTFLAGS`
เมื่อใช้ Cargo เพื่อบิลด์โปรเจกต์

</div>

### Rustfmt

[Rustfmt] เป็นเครื่องมือที่มาพร้อมกับ Rust ใช้จัดรูปแบบโค้ดของคุณตามแนวทางสไตล์

แนวทางเหล่านี้สามารถปรับแต่งให้เหมาะกับความต้องการของคุณได้โดยสร้างไฟล์ `rustfmt.toml` หรือ
`.rustfmt.toml` ไว้ที่รากของโปรเจกต์ ไฟล์นี้จะถูกใช้ในการเขียนทับ
การตั้งค่าเริ่มต้น ตัวอย่างเช่น:

```toml
# Set the maximum line width to 120
max_width = 120
# Maximum line length for single line if-else expressions
single_line_if_else_max_width = 40
```

สำหรับข้อมูลเพิ่มเติมเกี่ยวกับแนวทางที่ `rustfmt` จะตรวจสอบ โปรดดู
[หนังสือแนวทางสไตล์ Rust @rust-style]

<div class="reco" id="DENV-FORMAT" type="ข้อเสนอแนะ" title="ใช้ตัวจัดรูปแบบ Rust (rustfmt)">

ควรใช้เครื่องมือ `rustfmt` เพื่อให้แน่ใจว่าฐานโค้ด (codebase) ปฏิบัติตาม
แนวทางสไตล์

</div>

[rustfmt]: https://github.com/rust-lang/rustfmt

### Cargo fix

คำสั่ง [`cargo fix`] เป็นเครื่องมือที่ใช้สำหรับ
การแก้ไขคำเตือนของคอมไพเลอร์ รวมทั้งช่วยให้การเปลี่ยนผ่านระหว่างเอดิชันเป็นไปได้ง่ายขึ้น

```shell
$ cargo fix
```

ในการเตรียมโปรเจกต์ Rust 2021 ให้เปลี่ยนผ่านไปยัง Rust 2024 สามารถเรียกใช้:

```shell
$ cargo fix --edition
```

Rustfix จะแก้ไขโค้ดให้เข้ากันได้กับ Rust 2024 หรือไม่ก็พิมพ์
คำเตือนที่อธิบายปัญหา ปัญหาดังกล่าวจะต้องแก้ไขด้วยตนเอง
การเรียกใช้คำสั่งซ้ำ ๆ (และอาจแก้ไขปัญหาบางอย่างด้วยตนเอง) จนกระทั่ง
ไม่มีคำเตือน จะทำให้มั่นใจได้ว่าโค้ดเข้ากันได้ทั้งกับ Rust 2021 และ
Rust 2024

ในการเปลี่ยนไปใช้ Rust 2024 อย่างถาวร อาจเรียกใช้:

```shell
$ cargo fix --edition-idioms
```

โปรดทราบว่าเครื่องมือนี้ให้การรับประกันเพียงเล็กน้อยเกี่ยวกับความถูกต้องตามหลักความปลอดภัย (soundness)
ของการแก้ไขที่เสนอ โดยเฉพาะอย่างยิ่ง การแก้ไขบางอย่าง (เช่นบางรายการ
ที่มาพร้อมกับ `--edition-idioms`) เป็นที่ทราบกันว่าทำให้การคอมไพล์ล้มเหลว
หรือเปลี่ยนความหมายของโปรแกรมในบางกรณี

[`cargo fix`]: https://doc.rust-lang.org/cargo/commands/cargo-fix.html


### Clippy

[Clippy] เป็นเครื่องมือที่ให้และตรวจสอบลินต์ (lint) จำนวนมาก (บั๊ก สไตล์ ปัญหา
ด้านประสิทธิภาพ ฯลฯ) ตั้งแต่เวอร์ชัน 1.29 เป็นต้นมา `clippy` สามารถใช้ได้ภายใน
สภาพแวดล้อม `rustup` ที่เป็น stable แนะนำให้ติดตั้ง `clippy` เป็นคอมโพเนนต์
(`rustup component add clippy`) ในชุดเครื่องมือ stable แทนที่จะติดตั้ง
เป็นดีเพนเดนซีของโปรเจกต์

เครื่องมือนี้มาพร้อมหมวดหมู่ลินต์บางประการตามประเภทของปัญหาที่มุ่งตรวจสอบ
โปรแกรมเมอร์ควรตรวจสอบคำเตือนเหล่านั้นซ้ำอีกครั้งก่อนที่จะคอมมิต
แนวทางแก้ไขที่ `clippy` เสนอ โดยเฉพาะอย่างยิ่งในกรณีของลินต์ใน
หมวดหมู่ `clippy::nursery` เนื่องจากคำแนะนำเหล่านั้นยังอยู่ระหว่างการพัฒนา

ปัจจุบัน `clippy` มีเครื่องมือ `fix` ที่คล้ายกับ `cargo fix`

[clippy]: https://github.com/rust-lang/rust-clippy

<div class="reco" id="DENV-LINTER" type="กฎ" title="ใช้ตัวตรวจโค้ดอย่างสม่ำเสมอ">

ต้องใช้ตัวตรวจโค้ด (linter) เช่น `clippy` อย่างสม่ำเสมอในระหว่างการพัฒนา
แอปพลิเคชันที่ปลอดภัย

</div>

<div class="reco" id="DENV-AUTOFIX" type="กฎ" title="ตรวจสอบการแก้ไขอัตโนมัติด้วยตนเอง">

ในการพัฒนา Rust ที่ปลอดภัย นักพัฒนาต้องตรวจสอบยืนยันการแก้ไขอัตโนมัติใด ๆ
(ตัวอย่างเช่น ที่มาจาก `rustfix` หรือ `clippy`)

</div>

### เครื่องมืออื่น ๆ

ยังมีเครื่องมือหรือคำสั่งย่อยของ `cargo` ที่มีประโยชน์อื่น ๆ สำหรับบังคับใช้
ความปลอดภัยของโปรแกรม ไม่ว่าจะโดยการค้นหาแพตเทิร์นโค้ดเฉพาะเจาะจง หรือโดยการมี
คำสั่งที่สะดวกสำหรับการทดสอบหรือการฟัซ (fuzzing) เครื่องมือเหล่านี้จะกล่าวถึง
ในบทถัดไป ตามวัตถุประสงค์ของแต่ละเครื่องมือ
