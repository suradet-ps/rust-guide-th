# อินเทอร์เฟซกับภาษาต่างประเทศ (FFI) { #chapter-ffi }

แนวทางของ Rust ในการอินเทอร์เฟซกับภาษาต่างประเทศอาศัยความเข้ากันได้อย่างแน่นแฟ้นกับภาษา C อย่างไรก็ตาม ขอบเขตนี้โดยธรรมชาติแล้วเป็น **unsafe** (ดู [หนังสือ Rust: Unsafe Rust])

[หนังสือ Rust: Unsafe Rust]: https://doc.rust-lang.org/book/ch19-01-unsafe-rust.html

ฟังก์ชันที่ถูกทำเครื่องหมายด้วย `extern` จะถูกทำให้เข้ากันได้กับโค้ด C ในระหว่างการคอมไพล์ ฟังก์ชันเหล่านี้อาจถูกเรียกจากโค้ด C ด้วยค่าพารามิเตอร์ใดๆ ก็ได้ รูปแบบที่แน่นอนคือ `extern "<ABI>"` โดยที่เอบีไอ (ABI) คือธรรมเนียมการเรียก (calling convention) และขึ้นอยู่กับแพลตฟอร์มเป้าหมาย ค่าเริ่มต้นคือ `C` ซึ่งสอดคล้องกับธรรมเนียมการเรียกมาตรฐานของภาษา C บนแพลตฟอร์มเป้าหมาย

```rust
{{#include ../../../examples/src/ffi.rs:mylib_f}}
```

เพื่อให้ฟังก์ชัน `mylib_f` สามารถเข้าถึงได้ด้วยชื่อเดียวกัน ฟังก์ชันนั้นต้องถูกกำกับด้วยแอตทริบิวต์ `#[unsafe(no_mangle)]` ด้วย

ในทางกลับกัน เราสามารถเรียกฟังก์ชัน C จาก Rust ได้ หากฟังก์ชันเหล่านั้นถูกประกาศไว้ในบล็อก `extern`:

```rust
{{#include ../../../examples/src/ffi.rs:import_c}}
```

<div class="note">

ฟังก์ชันต่างประเทศใดๆ ที่ถูกนำเข้าใน Rust ผ่านบล็อก `extern` จะถือเป็น **`unsafe` โดยอัตโนมัติ** ด้วยเหตุนี้ การเรียกฟังก์ชันต่างประเทศใดๆ จึงต้องกระทำจากบริบท `unsafe`

</div>

บล็อก `extern` ยังอาจมีการประกาศตัวแปรโกลบอลจากต่างประเทศที่ขึ้นต้นด้วยคีย์เวิร์ด `static` ได้ด้วย:

```rust
{{#include ../../../examples/src/ffi.rs:extern_static}}
```

## โครงสร้างโค้ด

<div class="reco" id="FFI-SAFEWRAPPING" type="ข้อเสนอแนะ" title="จัดเตรียมตัวห่อที่ปลอดภัยให้กับไลบรารีต่างประเทศ">

การอินเทอร์เฟซไลบรารีที่เขียนด้วยภาษาอื่นใน Rust ควรทำเป็นสองส่วน:

- โมดูลระดับต่ำ ซึ่งอาจถูก *ซ่อน* ไว้ โดยทำหน้าที่แปลง C API ต้นฉบับไปเป็นบล็อก `extern` อย่างใกล้เคียง
- โมดูลตัวห่อที่ปลอดภัย ซึ่งรับประกันความปลอดภัยของหน่วยความจำและอินแวเรียนต์ (invariant) ด้านความปลอดภัยในระดับ Rust

หาก API ระดับต่ำถูกเปิดเผยต่อสาธารณะ ควรทำในเครตแยกต่างหากที่มีชื่อในรูปแบบ `*-sys`

</div>

เครต [`rust-bindgen`] อาจถูกใช้เพื่อสร้างส่วนระดับต่ำของการผูก (binding) จากไฟล์ส่วนหัว (header) ของ C โดยอัตโนมัติ

## การกำหนดชนิดข้อมูล

การกำหนดชนิดข้อมูลเป็นวิธีที่ Rust ใช้รับประกันความปลอดภัยของหน่วยความจำ เมื่อต้องอินเทอร์เฟซกับภาษาต่างประเทศซึ่งอาจไม่ให้การรับประกันแบบเดียวกัน การเลือกชนิดข้อมูลในการผูกจึงเป็นสิ่งจำเป็นอย่างยิ่งต่อการรักษาความปลอดภัยของหน่วยความจำ

### การจัดวางข้อมูล

Rust ไม่ให้การรับประกันทั้งในระยะสั้นและระยะยาวเกี่ยวกับการจัดวางข้อมูลในหน่วยความจำ วิธีเดียวที่จะทำให้ข้อมูลเข้ากันได้กับภาษาต่างประเทศคือการใช้การจัดวางข้อมูล (data layout) ที่เข้ากันได้กับ C อย่างชัดเจนผ่านแอตทริบิวต์ `repr` (ดู [เอกสารอ้างอิง Rust: Type Layout]) ตัวอย่างเช่น ชนิดข้อมูล Rust ต่อไปนี้:

```rust
{{#include ../../../examples/src/ffi.rs:extern_struct}}
```

เข้ากันได้กับชนิดข้อมูล C ต่อไปนี้:

```c
{{#include ../../../examples/src/ffi.c:extern_struct}}
```

<div class="reco" id="FFI-CTYPE" type="กฎ" title="ใช้เฉพาะชนิดข้อมูลที่เข้ากันได้กับ C ใน FFI">

ในการพัฒนา Rust อย่างปลอดภัย ต้องไม่ใช้ชนิดข้อมูลที่ไม่เข้ากันได้กับ C เป็นพารามิเตอร์หรือชนิดข้อมูลที่คืนค่าของฟังก์ชันที่นำเข้าหรือส่งออก และเป็นชนิดของตัวแปรโกลบอลที่นำเข้าหรือส่งออก

ข้อยกเว้นเพียงประการเดียวคือชนิดข้อมูลที่ถือว่าเป็น **ทึบ (opaque)** ในฝั่งต่างประเทศ

</div>

ชนิดข้อมูลต่อไปนี้ถือว่าเข้ากันได้กับ C:

- ชนิดข้อมูลพื้นฐาน (primitive) แบบจำนวนเต็มหรือจำนวนจุดลอยตัว
- `struct` ที่กำกับด้วย `repr(C)`
- `enum` ที่กำกับด้วย `repr(C)` หรือ `repr(Int)` ซึ่งมีอย่างน้อยหนึ่ง variant และมีเฉพาะ variant ที่ไม่มีฟิลด์ (โดยที่ `Int` เป็นชนิดข้อมูลพื้นฐานแบบจำนวนเต็ม)
- ตัวชี้ดิบ (raw pointers)
- `Option<T>` โดยที่ `T` เป็นอย่างใดอย่างหนึ่งต่อไปนี้
  - `core::ptr::NonNull<U>` โดยที่ `U` เป็นชนิดข้อมูลที่เข้ากันได้กับ C และเป็น `Sized` ซึ่งในกรณีนี้จะเข้ากันได้กับพอยน์เตอร์ `*const T` และ `*mut T`
  - `core::num::NonZero*` ซึ่งจะเข้ากันได้กับชนิดข้อมูลพื้นฐานแบบจำนวนเต็มที่สอดคล้องกัน
- `struct` ที่กำกับด้วย `repr(transparent)` ซึ่งมีเพียงฟิลด์เดียว โดยฟิลด์นั้นมีชนิดข้อมูลที่เข้ากันได้กับ C

ชนิดข้อมูลต่อไปนี้ไม่เข้ากันได้กับ C:

- ชนิดข้อมูลที่มีขนาดเปลี่ยนแปลงได้ (dynamically sized types)
- ออบเจกต์เทรต (trait objects)
- enum ที่มีฟิลด์
- ทูเพิล (แต่โครงสร้างทูเพิลแบบ `repr(C)` ใช้ได้)

บางชนิดข้อมูลเข้ากันได้โดยมีข้อแม้บางประการ:

- ชนิดข้อมูลที่มีขนาดศูนย์ (zero-sized types) ซึ่งมีขนาดศูนย์จริงๆ (เรื่องนี้ไม่ได้รับการระบุใน C และขัดแย้งกับข้อกำหนดของ C++)
- enum ที่กำกับด้วย `repr(C)`, `repr(C, Int)` หรือ `repr(Int)` ซึ่งมีฟิลด์ (ดู [RFC 2195 @RFC-2195])

[เอกสารอ้างอิง Rust: Type Layout]: https://doc.rust-lang.org/reference/type-layout.html

### ความสอดคล้องของชนิดข้อมูล

<div class="reco" id="FFI-TCONS" type="กฎ" title="ใช้ชนิดข้อมูลที่สอดคล้องกันที่ขอบเขต FFI">

ชนิดข้อมูลต้องสอดคล้องกันในแต่ละฝั่งของขอบเขต FFI

แม้ว่ารายละเอียดบางอย่างอาจถูกซ่อนในฝั่งหนึ่งเมื่อเทียบกับอีกฝั่ง (โดยทั่วไปเพื่อทำให้ชนิดข้อมูลทึบ) แต่ชนิดข้อมูลทั้งสองฝั่งต้องมีขนาดเท่ากันและมีข้อกำหนดการจัดแนว (alignment) เดียวกัน

</div>

โดยเฉพาะอย่างยิ่งสำหรับ enum ที่มีฟิลด์ ชนิดข้อมูลที่สอดคล้องกันใน C (หรือ C++) ไม่ได้ชัดเจนโดยตัวมันเอง เทียบกับ [RFC 2195 @RFC-2195]

เครื่องมืออัตโนมัติสำหรับสร้างการผูก เช่น [`rust-bindgen`] หรือ [`cbindgen`] อาจช่วยให้ชนิดข้อมูลสอดคล้องกันระหว่าง C และ Rust ได้

<div class="reco" id="FFI-AUTOMATE" type="ข้อเสนอแนะ" title="ใช้เครื่องมือสร้างการผูกอัตโนมัติ">

ในการพัฒนา Rust อย่างปลอดภัย ควรใช้เครื่องมือสร้างอัตโนมัติเพื่อสร้างการผูกเมื่อเป็นไปได้ และดูแลรักษาการผูกเหล่านั้นอย่างต่อเนื่อง

</div>

### ชนิดข้อมูลที่ขึ้นอยู่กับแพลตฟอร์ม

เมื่ออินเทอร์เฟซกับภาษาต่างประเทศ เช่น C หรือ C++ มักจำเป็นต้องใช้ชนิดข้อมูลที่ขึ้นอยู่กับแพลตฟอร์ม เช่น `int`, `long` ของ C เป็นต้น

นอกเหนือจาก `c_void` ใน `std::ffi` (หรือ `core::ffi`) สำหรับ `void` แล้ว ไลบรารีมาตรฐานยังมีชื่อแทนแบบพอร์ตเทเบิล (portable type aliases) ใน `std:os::raw` (หรือ `core::os::raw`) ดังนี้:

- `c_char` สำหรับ `char` (เป็นได้ทั้ง `i8` หรือ `u8`)
- `c_schar` สำหรับ `signed char` (เป็น `i8` เสมอ)
- `c_uchar` สำหรับ `unsigned char` (เป็น `u8` เสมอ)
- `c_short` สำหรับ `short`
- `c_ushort` สำหรับ `unsigned short`
- `c_int` สำหรับ `int`
- `c_uint` สำหรับ `unsigned int`
- `c_long` สำหรับ `long`
- `c_ulong` สำหรับ `unsigned long`
- `c_longlong` สำหรับ `long long`
- `c_ulonglong` สำหรับ `unsigned long long`
- `c_float` สำหรับ `float` (เป็น `f32` เสมอ)
- `c_double` สำหรับ `double` (เป็น `f64` เสมอ)

เครต [`libc`] มีชนิดข้อมูลที่เข้ากันได้กับ C เพิ่มเติม ซึ่งครอบคลุมไลบรารีมาตรฐาน C ได้เกือบทั้งหมด

<div class="reco" id="FFI-PFTYPE" type="กฎ" title="ใช้ชื่อแทนแบบพอร์ตเทเบิล `c_*` เมื่อผูกกับชนิดข้อมูลที่ขึ้นอยู่กับแพลตฟอร์ม">

ในการพัฒนา Rust อย่างปลอดภัย เมื่ออินเทอร์เฟซกับโค้ดต่างประเทศที่ใช้ชนิดข้อมูลซึ่งขึ้นอยู่กับแพลตฟอร์ม เช่น `int` และ `long` ของ C โค้ด Rust ต้องใช้ชื่อแทนชนิดข้อมูลแบบพอร์ตเทเบิล เช่น ชื่อแทนที่ไลบรารีมาตรฐานหรือเครต [`libc`] จัดเตรียมไว้ แทนที่จะใช้ชนิดข้อมูลเฉพาะแพลตฟอร์ม เว้นแต่การผูกนั้นถูกสร้างขึ้นโดยอัตโนมัติสำหรับแต่ละแพลตฟอร์ม (ดูหมายเหตุด้านล่าง)

</div>

### ชนิดข้อมูลที่ไม่ทนทาน: เรฟเฟอเรนซ์ ฟังก์ชันพอยน์เตอร์ และ enum {#robustness}

การแทนค่าแบบกับดัก (*trap representation*) ของชนิดข้อมูลหนึ่งๆ คือรูปแบบการแทนค่า (แพตเทิร์นของบิต) ที่เป็นไปตามข้อจำกัดการแทนค่าของชนิดนั้น (เช่น ขนาดและการจัดแนว) แต่ไม่ได้แทนค่าที่ถูกต้องของชนิดนั้น และนำไปสู่พฤติกรรมไม่นิยาม (undefined behavior / UB)

พูดง่ายๆ คือ หากตัวแปร Rust ถูกกำหนดให้เป็นค่าที่ไม่ถูกต้องเช่นนี้ ทุกสิ่งทุกอย่างสามารถเกิดขึ้นได้ ตั้งแต่โปรแกรมแครชธรรมดาไปจนถึงการรันโค้ดตามอำเภอใจ (arbitrary code execution) เมื่อเขียน safe Rust สิ่งนี้ไม่สามารถเกิดขึ้นได้ (ยกเว้นจากข้อบกพร่องในคอมไพเลอร์ Rust) อย่างไรก็ตาม เมื่อเขียน unsafe Rust และโดยเฉพาะอย่างยิ่งใน FFI สิ่งนี้เกิดขึ้นได้ง่ายมาก

ต่อไปนี้ **ชนิดข้อมูลที่ไม่ทนทาน** (non-robust types) คือชนิดข้อมูลที่มีการแทนค่าแบบกับดักดังกล่าว (อย่างน้อยหนึ่งรูปแบบ) ชนิดข้อมูล Rust จำนวนมากเป็นชนิดที่ไม่ทนทาน แม้แต่ในบรรดาชนิดข้อมูลที่เข้ากันได้กับ C:

- `bool` (1 ไบต์ มี 256 การแทนค่า แต่ถูกต้องเพียง 2 แบบ)
- เรฟเฟอเรนซ์
- ฟังก์ชันพอยน์เตอร์
- enum
- จำนวนจุดลอยตัว (แม้ว่าเกือบทุกภาษาจะมีความเข้าใจตรงกันว่าอะไรคือค่าจุดลอยตัวที่ถูกต้อง)
- ชนิดข้อมูลเชิงประกอบ (compound types) ที่มีฟิลด์ซึ่งเป็นชนิดไม่ทนทาน

ในทางกลับกัน ชนิดข้อมูลจำนวนเต็ม (`u*`/`i*`) และชนิดข้อมูลเชิงประกอบแบบแพ็ก (packed compound types) ที่ไม่มีฟิลด์ชนิดไม่ทนทาน ถือเป็นตัวอย่างของ *ชนิดข้อมูลที่ทนทาน* (robust types)

ชนิดข้อมูลที่ไม่ทนทานเป็นความยากลำบากเมื่อต้องอินเทอร์เฟซสองภาษา ปัญหาอยู่ที่การตัดสินใจว่า **ภาษาใดในสองภาษาจะรับผิดชอบในการยืนยันความถูกต้องของค่าที่ข้ามขอบเขต** และจะทำอย่างไร

<div class="reco" id="FFI-CKNONROBUST" type="กฎ" title="ต้องไม่ใช้ค่าต่างประเทศชนิดไม่ทนทานที่ไม่ได้ตรวจสอบ">

ในการพัฒนา Rust อย่างปลอดภัย ต้องไม่มีการใช้ค่าต่างประเทศที่เป็นชนิดไม่ทนทานโดย *ไม่ตรวจสอบ*

กล่าวอีกนัยหนึ่ง ฝ่าย Rust ต้องแปลงชนิดข้อมูลที่ทนทานไปเป็นชนิดข้อมูลที่ไม่ทนทานผ่านการตรวจสอบอย่างชัดเจน หรือฝั่งต่างประเทศต้องให้การรับประกันที่แน่นหนาเกี่ยวกับความถูกต้องของค่านั้น

</div>

<!-- -->

<div class="reco" id="FFI-CKINRUST" type="ข้อเสนอแนะ" title="ตรวจสอบค่าต่างประเทศใน Rust">

ในการพัฒนา Rust อย่างปลอดภัย ควรตรวจสอบความถูกต้องของค่าต่างประเทศใน Rust เมื่อเป็นไปได้

</div>

กฎทั่วไปเหล่านั้นต้องปรับให้เข้ากับภาษาต่างประเทศที่เฉพาะเจาะจงหรือความเสี่ยงที่เกี่ยวข้อง สำหรับภาษาแล้ว C ไม่เหมาะอย่างยิ่งต่อการให้การรับประกันเกี่ยวกับความถูกต้อง อย่างไรก็ตาม Rust ไม่ใช่ภาษาเดียวที่ให้การรับประกันที่แน่นหนา ตัวอย่างเช่น C++ บางส่วน (โดยไม่มีการตีความใหม่) อนุญาตให้นักพัฒนาเขียนการตรวจสอบชนิดข้อมูลได้มากมาย เนื่องจาก Rust แยกส่วน safe และ unsafe ออกจากกันโดยธรรมชาติ ข้อเสนอแนะคือให้ใช้ Rust ในการตรวจสอบเสมอเมื่อเป็นไปได้ ในส่วนของความเสี่ยง ชนิดข้อมูลที่อันตรายที่สุดคือเรฟเฟอเรนซ์ ฟังก์ชันเรฟเฟอเรนซ์ และ enum ซึ่งจะกล่าวถึงด้านล่าง

<div class="warning">

`bool` ของ Rust ถูกทำให้เทียบเท่ากับ `_Bool` ของ C99 (มีนามแฝงเป็น `bool` ใน `<stdbool.h>`) และ `bool` ของ C++ อย่างไรก็ตาม การโหลดค่าที่ไม่ใช่ 0 และ 1 เป็น `_Bool`/`bool` เป็นพฤติกรรมไม่นิยาม *ทั้งสองฝั่ง* safe Rust รับประกันสิ่งนี้ คอมไพเลอร์ C และ C++ ที่เป็นไปตามมาตรฐานรับประกันว่าไม่มีค่าใดนอกจาก 0 และ 1 ที่สามารถถูก *จัดเก็บ* ลงในค่า `_Bool`/`bool` ได้ แต่ไม่สามารถรับประกันได้ว่าจะไม่มีการ *ตีความใหม่ที่ไม่ถูกต้อง* (เช่น ชนิดยูเนียน การแคสต์พอยน์เตอร์) ในการตรวจจับการตีความใหม่ที่ไม่ดีเช่นนี้ อาจใช้แซนนิไทเซอร์ (sanitizer) เช่น `-fsanitize=bool` ของ [LLVM]

</div>

[LLVM]: https://llvm.org/

#### เรฟเฟอเรนซ์และพอยน์เตอร์

ชนิดข้อมูล `&mut T` และ `&T` อยู่ภายใต้ข้อกำหนดความถูกต้องเดียวกับชนิด T โดยมีข้อจำกัดเพิ่มเติมว่าต้องอ้างอิงถึงค่าที่ได้รับการจัดสรรหน่วยความจำอย่างถูกต้อง ส่วนเบี่ยงเบนใดๆ นำไปสู่พฤติกรรมไม่นิยาม

เมื่อผูกกับ C ทั้งขาเข้าและขาออก ปัญหาจะรุนแรงเป็นพิเศษ เพราะ C ไม่มีเรฟเฟอเรนซ์ (ในความหมายของพอยน์เตอร์ที่ถูกต้อง) และคอมไพเลอร์ไม่ให้การรับประกันด้านความปลอดภัยใดๆ

เมื่อผูกกับ C++ ในทางปฏิบัติเรฟเฟอเรนซ์ของ Rust อาจถูกผูกเข้ากับเรฟเฟอเรนซ์ของ C++ ได้ แม้ว่า ABI ที่แท้จริงของฟังก์ชัน `extern "C"` ใน C++ ที่มีเรฟเฟอเรนซ์จะเป็น “implementation-defined” (ขึ้นอยู่กับผู้พัฒนา) ก็ตาม นอกจากนี้ ควรตรวจสอบโค้ด C++ เพื่อป้องกันความสับสนระหว่างพอยน์เตอร์กับเรฟเฟอเรนซ์

เรฟเฟอเรนซ์ของ Rust อาจใช้ได้อย่างสมเหตุสมผลกับภาษาที่เข้ากันได้กับ C อื่นๆ รวมถึงตัวแปรของ C ที่อนุญาตให้ตรวจสอบชนิดข้อมูลแบบไม่เป็น null เช่น โค้ดที่กำกับด้วย Microsoft SAL

ในทางตรงกันข้าม ชนิดตัวชี้ดิบของ Rust (`*const T` และ `*mut T`) เลื่อนการตรวจสอบความถูกต้องจากจุดที่ผูกไปยังจุดที่ใช้งาน นอกจากนี้ ยังเปิดโอกาสให้ประเมินความถูกต้องโดยหลักเทียบกับ `std/core::ptr::null()` (`(void*)0` ของ C) แต่ในบางบริบทก็เทียบกับช่วงหน่วยความจำที่ทราบว่าถูกต้องได้ด้วย (โดยเฉพาะในระบบฝังตัวหรือการเขียนโปรแกรมระดับเคอร์เนล) หรือเทียบกับข้อกำหนดการจัดแนว

ข้อดีอีกประการของการใช้พอยน์เตอร์ของ Rust ใน FFI คือการโหลดค่าที่ถูกชี้ไปจะถูกทำเครื่องหมายอย่างชัดเจนว่าอยู่ในบล็อกหรือฟังก์ชัน `unsafe`

<div class="reco" id="FFI-CK-PTR-VALID" type="กฎ" title="ตรวจสอบพอยน์เตอร์ต่างประเทศ">

ในการพัฒนา Rust อย่างปลอดภัย โค้ด Rust ใดๆ ที่ดีเรฟเฟอเรนซ์ (dereference) พอยน์เตอร์ต่างประเทศ ต้องตรวจสอบความถูกต้องของพอยน์เตอร์นั้นก่อนล่วงหน้า โดยเฉพาะอย่างยิ่ง ต้องตรวจสอบว่าพอยน์เตอร์ไม่เป็น null ก่อนการใช้งานทุกครั้ง

ควรใช้แนวทางที่เข้มงวดกว่าเมื่อเป็นไปได้ ซึ่งรวมถึงการตรวจสอบพอยน์เตอร์เทียบกับช่วงหน่วยความจำที่ทราบว่าถูกต้อง การติดแท็ก (หรือลงลายเซ็น) พอยน์เตอร์ (ใช้ได้เป็นพิเศษหากค่าที่ถูกชี้ไปถูกจัดการจากฝั่ง Rust เท่านั้น) หรือการตรวจสอบการจัดแนวของข้อมูล

</div>

<div class="reco" id="FFI-INPUT-PTR" type="ข้อเสนอแนะ" title="ใช้ raw pointer เพื่อเข้ารหัสพอยน์เตอร์ที่มาจากภาษาภายนอก">

ในการพัฒนา Rust อย่างปลอดภัย ควรเข้ารหัสพอยน์เตอร์ที่รับมาจากภาษาภายนอกด้วย *ตัวชี้ดิบ* ของ Rust

ข้อยกเว้นได้แก่:

- เรฟเฟอเรนซ์ของ Rust ที่เป็นแบบทึบในภาษาต่างประเทศและถูกจัดการจากฝั่ง Rust เท่านั้น
- เรฟเฟอเรนซ์ที่ห่อด้วย `Option` (ดูหมายเหตุด้านล่าง)
- เรฟเฟอเรนซ์ที่ผูกกับเรฟเฟอเรนซ์ที่ปลอดภัยของภาษาต่างประเทศ เช่น จาก C รูปแบบเสริมบางตัว หรือจาก C++ ที่คอมไพล์ในสภาพแวดล้อมซึ่งเรฟเฟอเรนซ์ของ `extern "C"` ถูกเข้ารหัสเป็นพอยน์เตอร์

</div>

ในกรณีที่ไม่สามารถใช้ข้อเสนอแนะก่อนหน้านี้ได้ การตรวจสอบความถูกต้องของพอยน์เตอร์ต้องดำเนินการโดยภาษาซึ่งเป็นต้นทางของพอยน์เตอร์นั้น (กล่าวคือ ภาษาภายนอก)

<div class="reco" id="FFI-CK-INPUT-REF-VALID" type="กฎ" title="ต้องไม่ใช้เรฟเฟอเรนซ์ต่างประเทศที่ไม่ได้ตรวจสอบ">

ในการพัฒนา Rust อย่างปลอดภัย เรฟเฟอเรนซ์ต่างประเทศทุกตัวที่ถูกส่งมายัง Rust ผ่าน FFI ต้องถูก **ตรวจสอบที่ฝั่งต่างประเทศ** ไม่ว่าจะโดยอัตโนมัติ (เช่น โดยคอมไพเลอร์) หรือด้วยมือ

ข้อยกเว้นได้แก่เรฟเฟอเรนซ์ของ Rust ที่อยู่ในการห่อแบบทึบซึ่งถูกสร้างและจัดการจากฝั่ง Rust เท่านั้น และเรฟเฟอเรนซ์ที่ห่อด้วย `Option` (ดูหมายเหตุด้านล่าง)

</div>

#### ฟังก์ชันพอยน์เตอร์

ฟังก์ชันพอยน์เตอร์ที่ข้ามขอบเขต FFI อาจนำไปสู่การรันโค้ดตามอำเภอใจในที่สุด และถือเป็นความเสี่ยงด้านความปลอดภัยที่แท้จริง

<div class="reco" id="FFI-MARKEDFUNPTR" type="กฎ" title="ทำเครื่องหมายชนิดฟังก์ชันพอยน์เตอร์ใน FFI ว่าเป็น `extern` และ `unsafe`">

ในการพัฒนา Rust อย่างปลอดภัย ชนิดฟังก์ชันพอยน์เตอร์ใดๆ ที่ขอบเขต FFI ต้องถูกทำเครื่องหมายว่าเป็น `extern` (อาจระบุ ABI ที่เฉพาะเจาะจง) และ `unsafe`

</div>

- ใช้ฟังก์ชันพอยน์เตอร์ที่ห่อด้วย `Option` แล้วตรวจสอบเทียบกับ `null`:

  ```rust,noplaypen
  {{#include ../../../examples/src/ffi.rs:function_pointers}}
  ```

  ทางฝั่ง C:

  ```c
  {{#include ../../../examples/src/ffi.c:function_pointers}}
  ```

- ใช้พอยน์เตอร์ดิบพร้อมการแปลงชนิด (transmutation) แบบ `unsafe` ไปเป็นชนิดฟังก์ชันพอยน์เตอร์ ซึ่งอนุญาตให้ตรวจสอบได้ทรงพลังกว่า แลกมาด้วยความสะดวกในการใช้งานที่ลดลง

<div class="reco" id="FFI-CKFUNPTR" type="กฎ" title="ตรวจสอบฟังก์ชันพอยน์เตอร์ต่างประเทศ">

ในการพัฒนา Rust อย่างปลอดภัย ฟังก์ชันพอยน์เตอร์ต่างประเทศใดๆ ต้องถูกตรวจสอบที่ขอบเขต FFI

เมื่อผูกกับ C หรือแม้แต่ C++ ไม่สามารถรับประกันความถูกต้องของฟังก์ชันพอยน์เตอร์ได้อย่างง่ายดาย ยิ่งไปกว่านั้น ออบเจกต์ฟังก์ชันของ C++ (หรือที่เรียกว่าฟังก์เตอร์) ไม่เข้ากันได้กับ C

#### ชนิด enum

โดยปกติแล้ว แพตเทิร์นบิตที่เป็นไปได้ของค่า `enum` ที่ถูกต้องนั้นมีจำนวนน้อยมากเมื่อเทียบกับจำนวนแพตเทิร์นบิตทั้งหมดที่เป็นไปได้ในขนาดเดียวกัน การจัดการค่าของ `enum` ที่ให้มาโดยโค้ดต่างประเทศอย่างผิดพลาดอาจนำไปสู่การสับสนชนิดข้อมูล (type confusion) และส่งผลร้ายแรงต่อความปลอดภัยของซอฟต์แวร์ น่าเสียดายที่การตรวจสอบค่าของ `enum` ที่ขอบเขต FFI ไม่ใช่เรื่องง่ายสำหรับทั้งสองฝั่ง

ทางฝั่ง Rust การทำเช่นนี้ประกอบด้วยการใช้ชนิดข้อมูลจำนวนเต็มในประกาศบล็อก `extern` ซึ่งเป็นชนิดที่ *ทนทาน* แล้วจึงดำเนินการแปลงไปเป็นชนิด enum อย่างมีการตรวจสอบ

ทางฝั่งต่างประเทศ จะเป็นไปได้ก็ต่อเมื่อภาษานั้นอนุญาตให้ตรวจสอบที่เข้มงวดกว่าภาษา C ธรรมดา ตัวอย่างเช่น `enum class` ใน C++ ก็ใช้ได้ อย่างไรก็ตาม โปรดทราบว่าเช่นเดียวกับกรณีของเรฟเฟอเรนซ์ ABI ที่แท้จริงของ `extern "C"` สำหรับ `enum class` นั้นเป็น implementation-defined และควรได้รับการตรวจสอบสำหรับแต่ละสภาพแวดล้อม

<div class="reco" id="FFI-NOENUM" type="กฎ" title="ต้องไม่ใช้ `enum` ของ Rust ที่รับเข้ามาที่ขอบเขต FFI">

ในการพัฒนา Rust อย่างปลอดภัย เมื่ออินเทอร์เฟซกับภาษาต่างประเทศ โค้ด Rust ต้องไม่ยอมรับค่าที่รับเข้ามาซึ่งมีชนิดเป็น `enum` ใดๆ ของ Rust

ข้อยกเว้นได้แก่ชนิด `enum` ของ Rust ที่:

- เป็นแบบทึบในภาษาต่างประเทศและถูกจัดการจากฝั่ง Rust เท่านั้น
- ผูกกับ enum ที่ปลอดภัยในภาษาต่างประเทศ เช่น ชนิด `enum class` ใน C++

</div>

สำหรับ enum ที่ไม่มีฟิลด์ เครตอย่าง [`num_derive`] หรือ [`num_enum`] ช่วยให้นักพัฒนาจัดเตรียมการแปลงที่ปลอดภัยจากจำนวนเต็มไปเป็น enum ได้อย่างง่ายดาย และอาจถูกใช้เพื่อแปลงจำนวนเต็ม (ที่มาจาก `enum` ของ C) ไปเป็น enum ของ Rust อย่างปลอดภัย

[num_derive]: https://crates.io/crates/num_derive
[num_enum]: https://crates.io/crates/num_enum

การทำให้ชนิดข้อมูลทึบเป็นวิธีที่ดีในการเพิ่มความเป็นโมดูลาร์ในการพัฒนาซอฟต์แวร์ เมื่อพัฒนาแบบหลายภาษา สิ่งนี้เป็นเรื่องที่พบได้บ่อยมาก

<div class="reco" id="FFI-R-OPAQUE" type="ข้อเสนอแนะ" title="ใช้ชนิดข้อมูล Rust เฉพาะทางสำหรับชนิดข้อมูลทึบจากต่างประเทศ">

### การรักษาโมเดลหน่วยความจำของ Rust {#ffi-memory-model}

คอมไพเลอร์ Rust ใช้ข้อมูลจาก *borrow checker* ในการเพิ่มประสิทธิภาพการทำงานของโค้ด ในการนี้ คอมไพเลอร์สันนิษฐานว่าเงื่อนไขที่ borrow checker ตรวจสอบ โดยเฉพาะกฎเกี่ยวกับ[การตั้งชื่อแทนข้อมูลหลายทาง (aliasing)](https://doc.rust-lang.org/nomicon/aliasing.html) นั้นถูกต้อง และใช้สมมติฐานเหล่านี้เป็นฐานสำหรับการเพิ่มประสิทธิภาพ รายละเอียดเพิ่มเติมเกี่ยวกับโมเดลหน่วยความจำนี้สามารถพบได้ใน[เอกสาร API ของ `core` @memory-model]

การละเมิดสมมติฐานเหล่านี้จึงอาจนำไปสู่การเกิด UB ได้

ในการพัฒนาอย่างปลอดภัยใน Rust การใช้การอ้างอิงทางอ้อม (พอยน์เตอร์ เรฟเฟอเรนซ์) ที่ข้ามขอบเขต ต้องรักษาโมเดลหน่วยความจำของ Rust ไว้

</div>

## การจัดการหน่วยความจำและทรัพยากร

ภาษาโปรแกรมจัดการหน่วยความจำในรูปแบบที่แตกต่างกัน ด้วยเหตุนี้ เมื่อส่งข้อมูลระหว่าง Rust กับภาษาอื่น จึงเป็นเรื่องสำคัญที่ต้องทราบว่าภาษาใดเป็นผู้รับผิดชอบในการคืนพื้นที่หน่วยความจำของข้อมูลนั้น เช่นเดียวกันกับทรัพยากรชนิดอื่น เช่น ซ็อกเก็ตหรือไฟล์

Rust ติดตามความเป็นเจ้าของ (ownership) และไลฟ์ไทม์ (lifetime) ของตัวแปรเพื่อกำหนด ณ เวลาคอมไพล์ว่าหน่วยความจำควรถูกคืนหรือไม่และเมื่อใด ด้วยเทรต [`Drop`] เราสามารถใช้ประโยชน์จากระบบนี้เพื่อคืนทรัพยากรชนิดอื่น เช่น การเข้าถึงไฟล์หรือเครือข่าย การ *ย้าย* ข้อมูลบางส่วนจาก Rust ไปยังภาษาต่างประเทศย่อมหมายถึงการทิ้งการคืนทรัพยากรที่อาจเกี่ยวข้องกับข้อมูลนั้นไปด้วย

<div class="reco" id="FFI-MEM-NODROP" type="กฎ" title="ต้องไม่ใช้ชนิดข้อมูลที่ implement `Drop` ที่ขอบเขต FFI">

ในการพัฒนา Rust อย่างปลอดภัย โค้ด Rust ต้องไม่ implement [`Drop`] สำหรับชนิดข้อมูลใดๆ ที่ถูกส่งโดยตรงไปยังโค้ดต่างประเทศ (กล่าวคือ ไม่ผ่านพอยน์เตอร์หรือเรฟเฟอเรนซ์)

</div>

อันที่จริง ควรใช้เฉพาะชนิดข้อมูลที่เป็น `Copy` เท่านั้น โปรดทราบว่า `*const T` เป็น `Copy` แม้ว่าตัว T เองจะไม่เป็นก็ตาม

อย่างไรก็ตาม หากการไม่คืนหน่วยความจำและทรัพยากรเป็นเรื่องที่ไม่ดี การใช้หน่วยความจำที่ถูกคืนไปแล้วหรือการคืนทรัพยากรบางอย่างซ้ำสองครั้งกลับแย่ยิ่งกว่าจากมุมมองด้านความปลอดภัย เพื่อที่จะปล่อยทรัพยากรอย่างถูกต้องเพียงครั้งเดียว จำเป็นต้องทราบว่าภาษาใดเป็นผู้รับผิดชอบในการจัดสรรและคืนหน่วยความจำ

<div class="reco" id="FFI-MEM-OWNER" type="กฎ" title="รับประกันความเป็นเจ้าของข้อมูลที่ชัดเจนใน FFI">

ในการพัฒนา Rust อย่างปลอดภัย เมื่อข้อมูลชนิดใดๆ ผ่านขอบเขต FFI โดยไม่ถูกคัดลอก ต้องรับประกันว่า:

- ภาษาเดียวเท่านั้นที่รับผิดชอบทั้งการจัดสรรและการคืนหน่วยความจำของข้อมูล
- ภาษาอีกฝ่ายต้องไม่จัดสรรหรือคืนหน่วยความจำของข้อมูลนั้นโดยตรง แต่ต้องใช้ฟังก์ชันต่างประเทศเฉพาะทางที่ภาษาที่เลือกจัดเตรียมไว้

</div>

ความเป็นเจ้าของเพียงอย่างเดียวไม่เพียงพอ ยังคงต้องรับประกันไลฟ์ไทม์ที่ถูกต้อง โดยหลักคือไม่ให้มีการใช้งานใดๆ เกิดขึ้นหลังการคืนหน่วยความจำ ซึ่งเป็นเรื่องที่ท้าทายมากกว่า เมื่อภาษาอื่นเป็นผู้รับผิดชอบหน่วยความจำ วิธีที่ดีที่สุดคือจัดเตรียมตัวห่อที่ปลอดภัยให้กับชนิดข้อมูลต่างประเทศ:

<div class="reco" id="FFI-MEM-WRAPPING" type="ข้อเสนอแนะ" title="ห่อข้อมูลต่างประเทศด้วยตัวห่อที่คืนหน่วยความจำ">

ในการพัฒนา Rust อย่างปลอดภัย ข้อมูลต่างประเทศที่ไม่ละเอียดอ่อนใดๆ ที่ถูกจัดสรรและคืนหน่วยความจำในภาษาต่างประเทศ ควรถูกห่อหุ้มไว้ในชนิดข้อมูล [`Drop`] ในลักษณะที่ให้การคืนหน่วยความจำโดยอัตโนมัติใน Rust ผ่านการเรียกฟังก์ชันคืนหน่วยความจำของภาษาต่างประเทศโดยอัตโนมัติ

</div>

ตัวอย่างง่ายๆ ของการห่อของ Rust ครอบชนิดข้อมูลทึบภายนอก:

```rust,ignore,noplaypen
{{#include ../../../examples/src/ffi.rs:drop_extern}}
```
<div class="warning">

เนื่องจากการแพนิกอาจทำให้เมธอด `Drop::drop` ไม่ถูกเรียกใช้ วิธีนี้จึงไม่เพียงพอสำหรับการคืนหน่วยความจำข้อมูลที่ละเอียดอ่อน (เช่น การล้างข้อมูลที่ละเอียดอ่อน) เว้นแต่จะรับประกันได้ว่าโค้ดจะไม่เกิดการแพนิกเลย

สำหรับการล้างข้อมูลที่ละเอียดอ่อน อาจจัดการปัญหานี้ด้วยตัวจัดการการแพนิก (panic handler) เฉพาะทาง

</div>

เมื่อภาษาต่างประเทศเป็นฝ่ายใช้ประโยชน์จากทรัพยากรที่ Rust จัดสรรไว้ การให้การรับประกันใดๆ จะยากขึ้นมาก

ตัวอย่างเช่น ใน C ไม่มีวิธีง่ายๆ ในการตรวจสอบว่าเดสทรักเตอร์ที่เหมาะสมถูกเรียกใช้หรือไม่ แนวทางหนึ่งที่เป็นไปได้คือใช้ประโยชน์จากคอลแบ็ก (callback) เพื่อให้แน่ใจว่าการคืนทรัพยากรเกิดขึ้นจริง

โค้ด Rust ต่อไปนี้เป็นตัวอย่างที่ **ไม่ปลอดภัยต่อเธรด** (thread-unsafe) ของ API ที่เข้ากันได้กับ C ซึ่งจัดเตรียมคอลแบ็กเพื่อรับประกันการคืนทรัพยากรอย่างปลอดภัย:


## การแพนิกกับโค้ดต่างประเทศ {#ffi-panic}

เมื่อเรียกโค้ด Rust จากภาษาอื่น (เช่น C) โค้ด Rust ควรระมัดระวังไม่ให้เกิดการแพนิกเลย ตั้งแต่เวอร์ชัน [1.81.0](https://releases.rs/docs/1.81.0/) เป็นต้นมา การคลี่คลายสแต็ก (stack unwinding) จากโค้ด Rust เข้าสู่โค้ดต่างประเทศไม่ถือเป็นพฤติกรรมไม่นิยามอีกต่อไป แต่ขอแนะนำให้แยกการคลี่คลายสแต็กระหว่างภาษาอย่างเคร่งครัด เพื่อป้องกันการยุติโปรแกรมโดยไม่พึงประสงค์ที่อาจเกิดขึ้น[^ffi-panic-abort]

[^ffi-panic-abort]: รายละเอียดเพิ่มเติมสามารถพบได้ใน[ข้อกำหนดว่าด้วยการคลี่คลายสแต็ก (unwinding) @unwinding]

<div class="reco" id="FFI-NOPANIC" type="ข้อเสนอแนะ" title="จัดการ `panic!` อย่างถูกต้องใน FFI">

โค้ด Rust ที่ถูกเรียกจาก FFI ควรรับประกันว่าฟังก์ชันไม่สามารถแพนิกได้ หรือใช้กลไกจัดการการแพนิก (เช่น [`std::panic::catch_unwind`], [`std::panic::set_hook`], [`#[panic_handler]`](https://doc.rust-lang.org/reference/panic.html#r-panic.panic_handler)) เพื่อรับประกันว่าโค้ด Rust จะไม่ยุติโปรแกรมหรือคืนค่าในสถานะที่ไม่เสถียร

</div>

โปรดทราบว่า [`catch_unwind`] จะจับเฉพาะการแพนิกที่เกิดจากการคลี่คลายสแต็กเท่านั้น ไม่จับการแพนิกที่ยุติโปรเซส

```rust,unsafe,noplaypen,ignore
{{#include ../../../examples/src/ffi.rs:panic}}
```

### `no_std`

ในกรณีของโปรแกรม `#![no_std]` ต้องมีการนิยามตัวจัดการการแพนิก ([`#[panic_handler]`](https://doc.rust-lang.org/reference/panic.html#r-panic.panic_handler)) เพื่อรับประกันความปลอดภัย ควรเขียนตัวจัดการการแพนิกด้วยความระมัดระวังอย่างยิ่ง เพื่อรับประกันทั้งความปลอดภัย (safety) และความมั่นคงปลอดภัย (security) ของโปรแกรม

อีกแนวทางหนึ่งคือเพียงรับประกันว่าไม่มีการใช้ `panic!` เลย โดยใช้เครต [`panic-never`] เช่นเดียวกับ [`no-panic`] เครต [`panic-never`] อาศัยเทคนิคการลิงก์: ตัวลิงก์จะล้มเหลวหากสาขาที่ตายแล้วอย่างไม่ชัดเจน (non-trivially-dead branch) นำไปสู่ `panic!`

[`panic-never`]: https://crates.io/crates/panic-never
[`no-panic`]: https://crates.io/crates/no-panic
