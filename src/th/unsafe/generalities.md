# ข้อมูลทั่วไปเกี่ยวกับ `unsafe`

## การดำเนินการแบบ *unsafe*

โค้ด unsafe ช่วยขยายความสามารถของภาษาได้ รายการความสามารถเหล่านี้ทั้งหมดระบุไว้ใน[เอกสารอ้างอิง Rust](https://doc.rust-lang.org/reference/unsafety.html)
ความสามารถเหล่านี้อาจจำเป็นสำหรับการเขียนโปรแกรมเชิงระบบ แต่การใช้ความสามารถเหล่านี้ทำให้ภาษาเสีย[คุณสมบัติด้านความปลอดภัย](../guarantees.md#การรับประกันของภาษา)ของตนไป และอาจทำให้เกิดพฤติกรรมไม่นิยาม (undefined behavior) ได้

<div class="reco" id="UNSAFE-NOUB" type="กฎ" title="ต้องไม่มีพฤติกรรมไม่นิยาม">

ต้องไม่อนุญาตให้เกิดพฤติกรรมไม่นิยาม

</div>

## คีย์เวิร์ดหนึ่งคำที่มีการใช้งานสองแบบ

ตามที่อธิบายไว้ใน[เอกสารอ้างอิง Rust @rust-reference] คีย์เวิร์ด `unsafe` ถูกใช้ทั้งเพื่อทำเครื่องหมายความไม่ปลอดภัยใน API และเพื่อปลดล็อกความไม่ปลอดภัยในการนำไปใช้

### การทำเครื่องหมายด้วย `unsafe`

การทำเครื่องหมายด้วย `unsafe` เป็นการมอบความรับผิดชอบเกี่ยวกับความปลอดภัยของหน่วยความจำ (memory safety) จากผู้เขียน API ไปยังผู้ใช้ API
การใช้คีย์เวิร์ดนี้ใน API จะ*เตือน*ผู้ใช้ API ถึงผลกระทบที่อาจเป็นอันตรายจากการใช้ API นั้น

* ในลายเซ็นของฟังก์ชัน (หัวข้อ [`r-unsafe.fn`] ของ[เอกสารอ้างอิง Rust @rust-reference]) `unsafe` หมายความว่าพฤติกรรมของฟังก์ชันอาจนำไปสู่ UB ได้ หากการใช้ฟังก์ชันไม่เป็นไปตามสัญญาของอินเทอร์เฟซ (ที่อธิบายไว้อย่างไม่เป็นทางการในเอกสารประกอบ)
* ในประกาศเทรต (หัวข้อ [`r-unsafe.trait`] ของ[เอกสารอ้างอิง Rust @rust-reference]) `unsafe` หมายความว่าการนำเทรตนี้ไปใช้อย่างผิดพลาดอาจนำไปสู่ UB ได้ หากไม่ปฏิบัติตามสัญญาของการนำไปใช้ (ซึ่งควรมีเอกสารกำกับ)

[`r-unsafe.fn`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.fn>
[`r-unsafe.trait`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.trait>

### การปลดล็อกด้วย `unsafe`

การปลดล็อกด้วย `unsafe` หมายถึงการรับผิดชอบด้านความปลอดภัยของหน่วยความจำจากคอมไพเลอร์มาสู่ผู้พัฒนา

การใช้บล็อก `unsafe` ในตัวฟังก์ชันหรือในประกาศค่าคงที่นั้นถูกบังคับโดยคอมไพเลอร์ (หัวข้อ [`r-unsafe.block`] ของ[เอกสารอ้างอิง Rust @rust-reference]) เพื่อป้องกันไม่ให้ใช้ความสามารถของ `unsafe` อย่าง*ไม่ตั้งใจ* เช่น

* การใช้ฟังก์ชันที่ติดแท็ก `unsafe`
* การแก้ไขตัวแปร static
* การใช้ฟังก์ชัน `extern`

ในทำนองเดียวกัน การนำเทรต `unsafe` ไปใช้จำเป็นต้องใช้ `unsafe` (หัวข้อ [`r-unsafe.impl`] ของ[เอกสารอ้างอิง Rust @rust-reference]) เพื่อให้ผู้พัฒนาคำนึงถึงสัญญาด้านความปลอดภัยของหน่วยความจำอย่างชัดเจน คีย์เวิร์ด `unsafe` *ปลดล็อก*การนำเทรต `unsafe` ไปใช้

ท้ายที่สุด นับตั้งแต่เอดิชัน (edition) 2024 เป็นต้นมา `unsafe` ยังจำเป็นสำหรับการปลดล็อกสิ่งต่อไปนี้:

* บล็อก `extern` (หัวข้อ [`r-unsafe.extern`] ของ[เอกสารอ้างอิง Rust @rust-reference]) ซึ่งบรรจุประกาศของฟังก์ชันและตัวแปรจากภายนอก สำหรับ [FFI](./ffi.md#chapter-ffi),
* แอตทริบิวต์บางอย่าง (ตัวอย่างเช่น no_mangle ดู [`r-attributes.safety`] ของ[เอกสารอ้างอิง Rust @rust-reference])

[`r-unsafe.impl`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.impl>
[`r-unsafe.block`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.block>
[`r-unsafe.extern`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.extern>
[`r-attributes.safety`]: <https://doc.rust-lang.org/reference/attributes.html#r-attributes.safety>

## ข้อจำกัดและข้อควรระวัง

หากจะถอดความจาก[Rustonomicon](https://doc.rust-lang.org/nomicon/) หลักการพื้นฐานของ Rust อาจสรุปได้ดังนี้:

<div class="important">

โค้ดที่ไม่ใช้ `unsafe` ไม่มีทางผิดพลาดได้

</div>

การใช้ระบบชนิดข้อมูลและระบบความเป็นเจ้าของ (ownership) ร่วมกันทำให้โปรแกรม Rust มีความปลอดภัยของหน่วยความจำในระดับสูง ด้วยวิธีนี้ ภาษาจึงช่วยป้องกันการล้นของหน่วยความจำ (memory overflow) การสร้างพอยน์เตอร์ null หรือพอยน์เตอร์ที่ไม่ถูกต้อง และการแข่งกันของข้อมูล (data race)

คำสัญญานี้ใช้ได้เฉพาะเมื่อโค้ดไม่ใช้คุณสมบัติ `unsafe` เท่านั้น เมื่อมีการใช้คุณสมบัติ `unsafe` คอมไพเลอร์ไม่สามารถรับประกันความปลอดภัยของหน่วยความจำได้อีกต่อไป ผู้พัฒนาจึงต้องรับประกันว่าโค้ดปฏิบัติตามอินแวเรียนต์ (invariant) ที่รับประกันความปลอดภัยของหน่วยความจำ

ด้วยเหตุนี้ จึงเป็นสิ่งสำคัญยิ่งที่จะจำกัดการใช้คุณสมบัติ `unsafe` ให้มากที่สุด:

<div class="reco" id="LANG-UNSAFE" type="กฎ" title="อย่าใช้บล็อก unsafe">

ในการพัฒนา Rust อย่างปลอดภัย ควรหลีกเลี่ยงบล็อก `unsafe` หรือต้องมีเหตุผลรองรับอย่างน้อยหนึ่งข้อจากข้อต่อไปนี้:

* อินเทอร์เฟซกับภาษาต่างประเทศของ Rust (Foreign Function Interface / FFI) ช่วยให้สามารถอธิบายฟังก์ชันที่มีการนำไปใช้ในภาษา C ได้ โดยใช้คำนำหน้า `extern "C"` การใช้ฟังก์ชันเช่นนี้จำเป็นต้องใช้คีย์เวิร์ด `unsafe` ต้องมีการกำหนดตัวห่อ (wrapper) ที่ “ปลอดภัย” เพื่อเรียกใช้โค้ด C อย่างปลอดภัยและราบรื่น

* สำหรับการเขียนโปรแกรมบนอุปกรณ์ฝังตัว (embedded device) รีจิสเตอร์และทรัพยากรอื่น ๆ มักถูกเข้าถึงผ่านที่อยู่หน่วยความจำแบบตายตัว ในกรณีนี้ จำเป็นต้องใช้บล็อก `unsafe` เพื่อกำหนดค่าเริ่มต้นและดีเรฟเฟอเรนซ์พอยน์เตอร์เหล่านั้นใน Rust เพื่อลดจำนวนการเข้าถึงแบบ unsafe ในโค้ดและช่วยให้นักพัฒนาระบุจุดเหล่านั้นได้ง่ายขึ้น ต้องจัดเตรียมชั้นนามธรรม (abstraction) ที่เหมาะสม (โครงสร้างข้อมูล
หรือโมดูล)

* เมื่อพบข้อจำกัดด้านประสิทธิภาพในโค้ดส่วนเล็ก ๆ (ตัวอย่างเช่น บัฟเฟอร์ zero-copy ที่ถูกแก้ไข ณ ตำแหน่งเดิม, ค่าใช้จ่ายส่วนเพิ่มจากการจัดสรรหน่วยความจำ, ฯลฯ)

นอกเหนือจากกรณีเหล่านี้แล้ว `#![forbid(unsafe_code)]` ต้องปรากฏที่รากของเครต (crate) (โดยปกติคือ `main.rs` หรือ `lib.rs`) เพื่อให้เกิดข้อผิดพลาดในการคอมไพล์หากมีการใช้ `unsafe` ในฐานโค้ด

</div>

หากจำเป็นต้องใช้ `unsafe` ผู้พัฒนามีหน้าที่รับผิดชอบที่จะ:

* รับประกันว่าการปลดล็อกด้วย `unsafe` จะไม่นำไปสู่ *UB*
* รับประกันว่าการทำเครื่องหมาย `unsafe` ทั้งหมดมีเอกสารกำกับอย่างถูกต้องและครบถ้วน เพื่อให้มั่นใจว่าจะไม่เกิด *UB* หากปฏิบัติตามเงื่อนไขการใช้งาน (อินแวเรียนต์)

นอกเหนือจากตัวโค้ด `unsafe` เองแล้ว การห่อหุ้มการใช้คุณสมบัติ `unsafe` ในคอมโพเนนต์ (เครตหรือโมดูล) อย่างเหมาะสมก็เป็นสิ่งสำคัญยิ่ง เพื่อฟื้นคืนการรับประกันความปลอดภัยของหน่วยความจำตามปกติของ Rust:

<div class="reco" id="LANG-UNSAFE-ENCP" type="กฎ" title="การห่อหุ้มคุณสมบัติ *unsafe*">

ในการพัฒนาคอมโพเนนต์ซอฟต์แวร์ Rust (เครตหรือโมดูล) อย่างปลอดภัย โค้ด
*unsafe* ทั้งหมดต้องถูกห่อหุ้มในลักษณะที่:

* ไม่ว่าจะเป็นกรณีที่เปิดเผยพฤติกรรมที่ปลอดภัยต่อผู้ใช้ โดยที่การปฏิสัมพันธ์แบบปลอดภัยใด ๆ
  ไม่สามารถนำไปสู่ UB (undefined behavior) ได้;
* หรือเปิดเผยคุณสมบัติที่ทำเครื่องหมายว่า unsafe ซึ่งเงื่อนไขการใช้งาน
  (เงื่อนไขก่อนหน้า (precondition), ลำดับการเรียกใช้ ฯลฯ) มีเอกสารกำกับครบถ้วน

</div>

ดังนั้น ฟังก์ชันที่ใช้การดำเนินการ `unsafe` จึงถือว่า *ปลอดภัย* ได้ หากการดำเนินการ `unsafe` นั้นไม่ก่อให้เกิด *UB* (undefined behavior) ใด ๆ เมื่อพิจารณาจากอินแวเรียนต์ของคอมโพเนนต์ (โดยทั่วไปคืออินแวเรียนต์ของชนิดข้อมูลสำหรับเมธอด) ในทางกลับกัน ฟังก์ชันที่ไม่มีบล็อก `unsafe` ต้องถูกทำเครื่องหมายว่าเป็น `unsafe` หากฟังก์ชันนั้นละเมิดอินแวเรียนต์เหล่านี้ ดังนั้น การเลือกและความรู้เกี่ยวกับอินแวเรียนต์เหล่านี้จึงเป็นสิ่งสำคัญยิ่งต่อการพัฒนาอย่างปลอดภัย

## ตัวอย่าง: การรักษาอินแวเรียนต์ของชนิดข้อมูล

โค้ดต่อไปนี้มาจาก[Rustonomicon](https://doc.rust-lang.org/nomicon/working-with-unsafe.html)
โค้ดนี้อาจนำไปใช้เพื่อสร้างชนิดข้อมูล `Vec` แบบกำหนดเองได้

```rust
{{#include ../../../examples/src/generalities.rs:naive_vec}}
```

ความถูกต้องตามหลักความปลอดภัย (soundness) และความปลอดภัยของโค้ดนี้ ขึ้นอยู่กับว่าไบต์ตั้งแต่ที่อยู่ `self.ptr` ไปจนถึง `self.ptr + self.cap * size_of<T>()` ได้รับการจัดสรรหน่วยความจำแล้ว

อินแวเรียนต์นี้สามารถถูกละเมิดได้ด้วยโค้ดที่*ปลอดภัย* ตัวอย่างเช่น

```rust bad
{{#include ../../../examples/src/generalities.rs:make_room}}
```

ฟังก์ชันนี้อาจจำเป็นสำหรับการใช้งานภายใน แต่ไม่ควรเปิดเผยใน API หรือควรถูกทำเครื่องหมายด้วยคีย์เวิร์ด `unsafe` เนื่องจากการใช้งานอาจนำไปสู่ UB
