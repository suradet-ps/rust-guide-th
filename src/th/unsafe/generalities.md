# ข้อมูลทั่วไปเกี่ยวกับ `unsafe`

## การดำเนินการแบบ *unsafe*

ความสามารถของภาษาสามารถขยายได้ด้วยโค้ด unsafe รายการคุณสมบัติเหล่านี้ทั้งหมดระบุไว้ใน[เอกสารอ้างอิง Rust](https://doc.rust-lang.org/reference/unsafety.html)
ความสามารถเหล่านี้อาจจำเป็นสำหรับการเขียนโปรแกรมเชิงระบบ แต่ความสามารถเหล่านั้นทำให้ภาษาสูญเสีย[คุณสมบัติด้านความปลอดภัย](../guarantees.md#การรับประกันของภาษา) ของตน และพฤติกรรมไม่นิยาม (Undefined Behavior) อาจเกิดขึ้นได้

<div class="reco" id="UNSAFE-NOUB" type="กฎ" title="ต้องไม่มีพฤติกรรมไม่นิยาม">

ต้องไม่อนุญาตให้เกิดพฤติกรรมไม่นิยาม

</div>

## คีย์เวิร์ดหนึ่งคำที่มีการใช้งานสองแบบ

ตามที่อธิบายไว้ใน[เอกสารอ้างอิง Rust @rust-reference] คีย์เวิร์ด `unsafe` ถูกใช้ทั้งเพื่อทำเครื่องหมายความไม่ปลอดภัยใน API และเพื่อปลดล็อกความไม่ปลอดภัยในการนำไปใช้งาน

### การทำเครื่องหมายด้วย `unsafe`

การทำเครื่องหมายด้วย `unsafe` เป็นการมอบความรับผิดชอบเกี่ยวกับความปลอดภัยของหน่วยความจำ (memory safety) จากผู้เขียน API ไปยังผู้ใช้ API
การใช้คีย์เวิร์ดนี้ใน API จะ*เตือน*ผู้ใช้ API ถึงผลกระทบที่เป็นอันตรายที่อาจเกิดขึ้นจากการใช้ API นั้น

* ในลายเซ็นของฟังก์ชัน (หัวข้อ [`r-unsafe.fn`] ของ[เอกสารอ้างอิง Rust @rust-reference]) `unsafe` หมายความว่าพฤติกรรมของฟังก์ชันอาจนำไปสู่ UB ได้ หากการใช้ฟังก์ชันไม่เป็นไปตามสัญญาของอินเทอร์เฟซ (ที่อธิบายอย่างไม่เป็นทางการไว้ในเอกสารประกอบ)
* ในประกาศเทรต (หัวข้อ [`r-unsafe.trait`] ของ[เอกสารอ้างอิง Rust @rust-reference]) `unsafe` หมายความว่าการนำเทรตนี้ไปใช้อย่างผิดพลาดอาจนำไปสู่ UB ได้ หากไม่ปฏิบัติตามสัญญาของการนำไปใช้ (ซึ่งควรมีเอกสารกำกับ)

[`r-unsafe.fn`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.fn>
[`r-unsafe.trait`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.trait>

### การปลดล็อกด้วย `unsafe`

การปลดล็อกด้วย `unsafe` หมายถึงการรับความรับผิดชอบด้านความปลอดภัยของหน่วยความจำจากคอมไพเลอร์มาสู่ผู้พัฒนา

การใช้บล็อก `unsafe` ในตัวฟังก์ชันหรือในประกาศค่าคงที่นั้นถูกบังคับโดยคอมไพเลอร์ (หัวข้อ [`r-unsafe.block`] ของ[เอกสารอ้างอิง Rust @rust-reference]) เพื่อป้องกันการ*ใช้งานโดยไม่ตั้งใจ*ซึ่งความสามารถของ `unsafe` เช่น

* การใช้ฟังก์ชันที่ติดแท็ก `unsafe`
* การแก้ไขตัวแปร static
* การใช้ฟังก์ชัน `extern`

ในทำนองเดียวกัน การนำเทรต `unsafe` ไปใช้จำเป็นต้องใช้ `unsafe` (หัวข้อ [`r-unsafe.impl`] ของ[เอกสารอ้างอิง Rust @rust-reference]) เพื่อให้ผู้พัฒนาตระหนักถึงสัญญาด้านความปลอดภัยของหน่วยความจำอย่างชัดเจน คีย์เวิร์ด `unsafe` *ปลดล็อก*การนำเทรต `unsafe` ไปใช้

ท้ายที่สุด นับตั้งแต่เอดิชัน (edition) 2024 เป็นต้นมา `unsafe` ยังจำเป็นสำหรับการปลดล็อกสิ่งต่อไปนี้:

* บล็อก `extern` (หัวข้อ [`r-unsafe.extern`] ของ[เอกสารอ้างอิง Rust @rust-reference]) ซึ่งบรรจุประกาศของฟังก์ชันและตัวแปรต่างประเทศ สำหรับ [FFI](./ffi.md#chapter-ffi),
* แอตทริบิวต์บางอย่าง (ตัวอย่างเช่น no_mangle ดู [`r-attributes.safety`] ของ[เอกสารอ้างอิง Rust @rust-reference])

[`r-unsafe.impl`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.impl>
[`r-unsafe.block`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.block>
[`r-unsafe.extern`]: <https://doc.rust-lang.org/reference/unsafe-keyword.html#r-unsafe.extern>
[`r-attributes.safety`]: <https://doc.rust-lang.org/reference/attributes.html#r-attributes.safety>

## ข้อจำกัดและข้อควรระวัง

เมื่อถอดความจาก[Rustonomicon](https://doc.rust-lang.org/nomicon/) หลักการพื้นฐานของ Rust สามารถสรุปได้ดังต่อไปนี้:

<div class="important">

โค้ดที่ไม่ใช้ `unsafe` ไม่มีทางผิดพลาดได้

</div>

การใช้ระบบชนิดข้อมูลและระบบความเป็นเจ้าของ (ownership) ร่วมกันบังคับใช้ความปลอดภัยของหน่วยความจำระดับสูงในโปรแกรม Rust ด้วยวิธีนี้ ภาษาจึงช่วยป้องกันการล้นของหน่วยความจำ (memory overflow) การสร้างพอยน์เตอร์ null หรือพอยน์เตอร์ที่ไม่ถูกต้อง และการแข่งกันของข้อมูล (data race)

คำสัญญานี้ใช้ได้เฉพาะเมื่อโค้ดไม่ใช้คุณสมบัติ `unsafe` เท่านั้น เมื่อมีการใช้คุณสมบัติ `unsafe` คอมไพเลอร์ไม่สามารถรับประกันความปลอดภัยของหน่วยความจำได้อีกต่อไป ผู้พัฒนาจึงต้องรับประกันว่าโค้ดปฏิบัติตามอินแวเรียนต์ (invariant) ที่รับประกันความปลอดภัยของหน่วยความจำ

ด้วยเหตุนี้ การจำกัดการใช้คุณสมบัติ `unsafe` ให้มากที่สุดเท่าที่เป็นไปได้จึงเป็นสิ่งสำคัญยิ่ง:

<div class="reco" id="LANG-UNSAFE" type="กฎ" title="อย่าใช้บล็อก unsafe">

ในการพัฒนา Rust อย่างปลอดภัย ควรหลีกเลี่ยงบล็อก `unsafe` หรือต้องมีเหตุผลรองรับด้วยอย่างน้อยหนึ่งข้อต่อไปนี้:

* อินเทอร์เฟซกับภาษาต่างประเทศของ Rust (Foreign Function Interface / FFI) ช่วยให้สามารถอธิบายฟังก์ชันที่นำไปใช้ในภาษา C ได้ โดยใช้คำนำหน้า `extern "C"` การใช้ฟังก์ชันเช่นนี้จำเป็นต้องใช้คีย์เวิร์ด `unsafe` ต้องมีการกำหนดตัวห่อ (wrapper) ที่ “ปลอดภัย” เพื่อเรียกโค้ด C อย่างปลอดภัยและราบรื่น

* สำหรับการเขียนโปรแกรมสำหรับอุปกรณ์ฝังตัว (embedded device) รีจิสเตอร์และทรัพยากรอื่นๆ มักถูกเข้าถึงผ่านที่อยู่หน่วยความจำแบบตายตัว ในกรณีนี้ จำเป็นต้องใช้บล็อก `unsafe` เพื่อกำหนดค่าเริ่มต้นและดีเรฟเฟอเรนซ์พอยน์เตอร์เหล่านั้นใน Rust เพื่อลดจำนวนการเข้าถึงแบบ unsafe ในโค้ดและช่วยให้นักพัฒนาแสดงจุดเหล่านั้นได้ง่ายขึ้น ต้องจัดเตรียมการนามธรรม (abstraction) ที่เหมาะสม (โครงสร้างข้อมูล
หรือโมดูล)

* เมื่อพบข้อจำกัดด้านประสิทธิภาพในโค้ดส่วนเล็กๆ (ตัวอย่างเช่น: บัฟเฟอร์ zero-copy ที่ถูกแก้ไข ณ ตำแหน่งเดิม, ค่าใช้จ่ายส่วนเพิ่มจากการจัดสรรหน่วยความจำ, ฯลฯ)

เว้นแต่ในกรณีเหล่านี้ `#![forbid(unsafe_code)]` ต้องปรากฏที่รากของเครต (crate) (โดยปกติคือ `main.rs` หรือ `lib.rs`) เพื่อสร้างข้อผิดพลาดในการคอมไพล์หากมีการใช้ `unsafe` ในโค้ดเบส

</div>

หากจำเป็นต้องใช้ `unsafe` เป็นความรับผิดชอบของผู้พัฒนาที่จะ:

* รับประกันว่าการใช้การปลดล็อก `unsafe` ไม่นำไปสู่ *UB*
* รับประกันว่าการทำเครื่องหมาย `unsafe` ทั้งหมดมีเอกสารกำกับอย่างถูกต้องและครบถ้วน เพื่อไม่ให้เกิด *UB* ได้หากปฏิบัติตามเงื่อนไขการใช้งาน (อินแวเรียนต์)

นอกเหนือจากตัวโค้ด `unsafe` เองแล้ว การห่อหุ้มการใช้คุณสมบัติ `unsafe` ในคอมโพเนนต์ (เครตหรือโมดูล) อย่างเหมาะสมก็เป็นสิ่งสำคัญยิ่ง เพื่อคืนการรับประกันความปลอดภัยของหน่วยความจำตามปกติของ Rust:

<div class="reco" id="LANG-UNSAFE-ENCP" type="กฎ" title="การห่อหุ้มคุณสมบัติ *unsafe*">

ในการพัฒนาคอมโพเนนต์ซอฟต์แวร์ Rust (เครตหรือโมดูล) อย่างปลอดภัย โค้ด
*unsafe* ทั้งหมดต้องถูกห่อหุ้มในลักษณะที่:

* ไม่ว่าจะเปิดเผยพฤติกรรมที่ปลอดภัยต่อผู้ใช้ ซึ่งการปฏิสัมพันธ์แบบปลอดภัยใดๆ
  ไม่สามารถนำไปสู่ UB (undefined behavior) ได้;
* หรือเปิดเผยคุณสมบัติที่ทำเครื่องหมายว่า unsafe ซึ่งมีเงื่อนไขการใช้งาน
  (เงื่อนไขก่อนหน้า (precondition), ลำดับการเรียกใช้ ฯลฯ) ที่มีเอกสารกำกับอย่างครบถ้วน

</div>

ดังนั้น ฟังก์ชันที่ใช้การดำเนินการ `unsafe` จึงถือว่า *ปลอดภัย* ได้ หากการดำเนินการ `unsafe` นั้นไม่ก่อให้เกิด *UB* (undefined behavior) ใดๆ เมื่อพิจารณาจากอินแวเรียนต์ของคอมโพเนนต์ (โดยทั่วไปคืออินแวเรียนต์ของชนิดข้อมูลสำหรับเมธอด) ในทางกลับกัน ฟังก์ชันที่ไม่มีบล็อก `unsafe` ต้องถูกทำเครื่องหมายว่าเป็น `unsafe` หากฟังก์ชันนั้นละเมิดอินแวเรียนต์เหล่านี้ ดังนั้น การเลือกและการทำความเข้าใจอินแวเรียนต์เหล่านี้จึงเป็นสิ่งสำคัญยิ่งต่อการพัฒนาอย่างปลอดภัย

